# 按应用协调本机与多设备音频

## 状态与已确认目标

2026-10-01，用户确认将本机协同重新定义为：应用使用音频输入时，保留它自己的输出，降低其他应用的输出。浏览器中的每个网页实例分别作为应用，不能把整个浏览器的保护或衰减当作网页级支持。远程协同采用同一原则，由输出所在设备按实际应用需求执行。

用户授权继续推进能力验证和提交本任务变更，并明确要求方案、计划收敛后先复核确认，再开始正式实现。本文是待复核任务包；正式代码、正式应用和既有产品文档尚未改动。已新增浏览器端点实验与最小扩展原型，并使用独立签名的 iPad 实验程序。旧产品文档中按设备整体音量执行的内容描述旧方案，不能作为本任务的验收标准。后续实现时须同步更新现有 PRD、技术契约、使用指南和验证记录。

## 现有证据与能力缺口

| 范围 | 已确认事实 | 对新方案的影响 |
| --- | --- | --- |
| Mac 输入 | `Mac/InputActivity.swift` 按 PID 观察活动输入，GUI 最终只取得数量与 `localRecording`。`Mac/Selection.swift` 可把部分辅助进程归到外层应用。 | 保留应用身份与输入状态，不能提前压成布尔值；身份归并仍需对目标应用验证。 |
| Mac 输出 | `Mac/OutputVolume.swift` 修改默认输出设备整体音量。 | 无法独立保留某应用输出，需要选择性音频处理。 |
| 浏览器 | Chromium 的音频服务在 Mac 上运行于独立进程；OS 进程身份不足以代表网页。 | 扩展提供网页身份；先验证能否映射到原生可独立控制的输出，再决定增益在哪里执行。 |
| 跨设备 | `Shared/PeerState.swift` 传递每个 peer 的 `quiet`、版本和租约；GUI 主要在需求整体开始、结束时执行。 | 必须能在来源变化而需求仍非空时重算保护与衰减。 |
| iPad | `RecordingActivity.sample()` 返回整体 `Bool?`；`VolumeCoordinator` 修改 `Audio/Video` 分类音量。 | 目前既不能识别任意第三方应用输入，也不能选择性控制其输出。 |

Mac 的 Process Tap 创建 API 自 macOS 14.2 可用，本机 SDK 标明 iOS 不可用；项目当前最低 macOS 为 14.0。功能可用性必须显式处理。Apple 的示例支持选择进程输出、抑制原始播放并取得音频流，且要求系统音频录制授权；它不是现成的任意应用音量属性。本项目已将不静音 Tap 用于独立输出测量，并通过最小增益重放实验；硬件端原声抑制、延迟及异常恢复仍待验收。

来源：[Apple Process Tap 示例](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)、[创建 API](https://developer.apple.com/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:))、[Chromium Audio Service](https://chromium.googlesource.com/chromium/src/+/main/services/audio/README.md)。

## 推荐的最小实现边界

### 本机身份与规则

使用“逻辑应用实例”表达参与者，底层 PID、AudioObjectID 或网页句柄只是本机绑定。原生应用按应用及运行实例归并；网页至少区分浏览器实例、profile、tab 和文档实例。网页导航、关闭重开以及数字 ID 复用不得继承旧来源身份。嵌入框架默认归入其所在顶层网页，单独网页窗口拥有独立身份；同站点两个标签页不能按域名合并。

输入参与、有效采集、安静需求和输出保护分别表达。软件静音可以停止有效采集与安静需求，但不能直接撤销收听保护。若某应用在回答或只收听阶段彻底关闭输入，须验证应用接入信号或提供用户明确保护，不能用瞬时声音能量推断会话结束。“静音后也持续降低背景以便听清”属于额外的收听优先语义，尚不能当作原有录音降噪规则已经确认。

有安静需求时，相关输出的协调增益保持 1，允许降低的其他输出使用接收端设定的衰减比例。多个请求合并为一个有效衰减值，不能层层相乘。保护并发输入应用的并集；受保护输出应及时解除本产品已施加的衰减，即使其他请求仍存在。系统音量和应用自身的音量继续归用户控制，解除协同时只撤销本产品增益，避免把用户的音量调整恢复成旧值。原有整机“整轮手动接管”语义需要随控制对象一并复核。

### Mac 原生应用执行

先限定默认输出设备。验证选定进程输出经 Process Tap 取得后，抑制其原始播放，在本机内存中施加增益并重放到原输出。受保护应用尽量保留原播放路径；需要衰减的应用才进入处理链。排除声邻自身重放，防止回路。选择少量明确进程验证，不先实现任意设备路由引擎，也不假设现有虚拟输入驱动具有输出混音能力。

处理链必须验证停止、权限失败、异常退出、进程更换和设备切换后的播放恢复，不能把持续静音作为失败状态。缓冲、采样率及设备时钟须按实测处理。最小重放实验已完成，尚未完成上述完整验收。

`experiments/SelectiveOutputProbe/` 只接管指定的 afplay 合成音源。macOS 15.4.1 内置扬声器路径上，60 秒运行得到 5624 次回调、0 个无效缓冲；独立测量器确认重放进程的 B 幅度为名义输入的 0.199886，未混入 A，默认设备与系统音量前后相同。这足以选择 Tap 加增益重放作为实现方向，但不证明扬声器端原声已被抑制。Process Tap 并非已证实的硬件静音后测量点，正式启用前须另外验证最终输出和异常恢复。

### 浏览器接入

首版以 Helium/Chromium 家族和 ChatGPT Voice 为基准。用户已接受每个参与标签页先调用一次扩展，新页面和跨站导航重新授权；这不意味着其他 Chromium 产品已完成兼容验收。Safari、Firefox 和 iPad 浏览器不以此次结果代替验证。

扩展是 Mac App 的本机适配器，不是独立 peer。设备仍是配对、跨设备连接、签名和租约的边界；Mac App 统一计算规则。扩展报告网页实例和参与状态，必要时执行 Mac 下发的逐页目标增益。增加执行能力不要求扩展拥有设备身份或独立的跨设备策略。

先验证用户提出的较小方案：扩展仅提供网页与音频来源的映射，由 Mac 统一执行增益。判定条件是网页必须对应原生端可独立寻址和控制的输出，不是只取得渲染进程 PID 或浏览器内部流编号。若原生端看到的是多个网页已混合的输出，补充身份信息不能把混音分离。Chrome 的 `processes.getProcessIdForTab` 返回渲染进程身份，且接口限 Dev channel，不能据此承诺生产版本的音频映射。Chromium 内部 `AudioOutputStream.SetVolume` 证明浏览器内部有逐流增益，但没有证明扩展或外部 App 可以调用。

该较小方案已于 2026-10-01 在 Helium 0.15.7.1 的同站点双页、默认输出路径上取得反例。普通可见窗口中，A 单独、A+B、B 单独三个阶段各八次采样，都只有相同的进程对象 101、PID 82245、输出设备 78 和唯一硬件流 79；全部停止后活动输出归零。浏览器同时显示相应页面正在播放。SDK 明确 `CATapDescription.stream` 是设备硬件流索引，不能传网页流 ID。因此当前 Process Tap 没有足够细的选择参数，继续补充网页元数据不能使这个执行器分别处理两页。结论不扩大为所有浏览器或所有原生接口均不可能。

实验位于 `experiments/BrowserAudioProbe/`，结果分析可运行 `python3 experiments/BrowserAudioProbe/analyze.py`。初次后台自动化标签页虽然显示 AudioContext running，却未形成 HAL 输出；该轮是无效归属样本，已与普通可见窗口结果分开保留。原生 afplay 正向对照确认采样器能够观察输出。

只有原生路径无法提供逐页隔离时，再验证 `tabCapture → AudioContext → GainNode → 输出`，由扩展执行逐页增益。Chrome 官方接口要求用户调用扩展才能启动标签页捕获，并对目标 tab 授权作限制。捕获会抑制该 tab 原始播放，因此扩展必须维持重放。已捕获流可跨页面导航持续，故音频捕获句柄和网页业务身份必须分别管理。不能把“安装一次扩展”解释为“所有未来网页可自动捕获”。

最小扩展已在 `experiments/BrowserAudioProbe/extension/` 加载并验证，只接受 `http://localhost:18763` 或 `http://127.0.0.1:18763` 的实验页，支持目标增益 1、0.2 与释放，90 秒自动结束捕获，不保存音频。消息来源、目标域及增益边界的模拟测试通过，实际弹窗也完成了双页同时接管、独立设置和逐页解除。浏览器工具禁止访问非 HTTP/HTTPS 管理页，因此由用户手动加载，没有通过其他控制路径绕过限制。原型没有配对、远程连接或独立 peer 身份，也未接入正式 Mac 策略。

2026-10-01，独立签名的 `SpectrumMeter.app` 用不静音 Process Tap 测量浏览器实际混合输出，A 的 440 Hz 合成音保持原播放路径，仅由扩展接管 B 的 660 Hz 合成音。以原始播放为基线，B 在 20%、100%、再次 20%、解除四个阶段的幅度比例分别为 0.199984、1.000013、0.200012、1.000045；A 各阶段中位幅度与基线的偏差均小于 0.01%。每阶段至少 15 个稳定半秒窗口，测量器正常结束，没有无效缓冲；结束后八次 HAL 采样确认浏览器活动输出归零。这证明该 Helium/默认输出路径/双 Web Audio 音源的逐页衰减和正常解除恢复，稳定输出未叠加未衰减的 B 原声。

测量前先以独立 `afplay` 已知合成音验证测量器，两路幅度均符合预期。浏览器实验原始样本、UI 操作时间戳与分析在 `local/BrowserAudioProbe/spectrum-*`；运行 `python3 experiments/BrowserAudioProbe/analyze-spectrum.py` 可复核目标、样本和增益。这是进程输出边界的验证，尚未覆盖切换瞬间、扬声器声学效果、延迟、音质、扩展崩溃/禁用、90 秒到期或导航恢复，也未覆盖 WebRTC、iframe 和任意网页输入识别。

使用 Native Messaging 传递小量身份、状态和控制消息；若采用扩展增益，音频留在浏览器内部。网页不能自行声明另一个标签页或设备的身份；身份由扩展的可信消息上下文绑定。页面脚本提供的参与信号只作为该网页的证据，不能直接获得整机控制权。默认不把网页标题、完整 URL 或音频发送给其他设备。

输入侧是独立缺口。核对过的 Chrome `tabs` API/schema 提供有声、静音等信息，未提供任意网页麦克风会话状态；`tabCapture.getCapturedTabs()` 观察的是扩展捕获，不能冒充网页使用麦克风。可先验证在获准页面的 `document_start`、MAIN world 观察 `getUserMedia` 与轨道生命周期，并将 iframe 状态归并到顶层网页。该方法会受注入时机、已存在流、页面干预和框架权限影响，必须标注证据及未知状态；需要稳定语义的网站可增加明确的应用接入。

只改 `<audio>/<video>.volume` 无法作为覆盖 Web Audio、WebRTC 及所有页面结构的统一方案。若公开扩展 API 的逐页授权或输入观测缺口无法满足自动协同要求，应研究浏览器内部的网页媒体状态和每路输出控制接口，或与浏览器项目合作；不能用整浏览器调音冒充完成，也不先承诺维护浏览器分支。

若最终由浏览器执行网页级增益，Mac 原生执行器须排除其已交由浏览器处理的音频路径，避免重复衰减。若 OS 只能区分整组浏览器音频，则整组排除原生衰减；未接入网页显示控制能力不足并保持原音量。这是覆盖不足，不是网页级目标已经交付。

来源：[Chrome tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture)、[后台捕获示例](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)、[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)、[内容脚本](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)、[tabs schema](https://chromium.googlesource.com/chromium/src/+/main/chrome/common/extensions/api/tabs.json)、[GainNode](https://developer.mozilla.org/en-US/docs/Web/API/GainNode)。

映射与内部控制依据：[Chrome processes](https://developer.chrome.com/docs/extensions/reference/api/processes)、[Chromium AudioOutputStream 定义](https://chromium.googlesource.com/chromium/src/+/main/media/mojo/mojom/audio_output_stream.mojom)。

### 多设备需求

沿用现有配对关系、点对点认证、版本和租约机制。发送端发布本机逻辑来源的需求快照，接收端根据本机输出、保护关系和执行能力决定如何响应。协议初步只需要设备命名空间下的来源实例 ID、是否请求背景衰减、可选的明确关联 ID，以及快照版本、有效期、已知状态与签名。PID、网页内部句柄和音频留在本机；背景增益由接收端设置。参与状态与需求分开，允许仍需保护但暂不请求安静的来源。

若输入在 Mac、相关输出在 iPad，需要用户或实际应用集成建立关联。相同应用名、域名、账号或近似开始时间都不足以证明同一活动。未关联不等于已知背景，跨设备自动模式应只衰减接收端已有依据允许降低的输出。两个独立活动保护各自相关输出，其余背景接受合并后的请求。来源掉线使需求按租约到期，不能因此把接收端仍有效的相关输出突然当成背景。

不需要为每个来源建立独立连接或新建全局会话服务。先采用每个发送设备一份完整快照；现有 Wi-Fi 帧限 1024 字节、部分 BLE 接收限 512 字节，须量出来源列表容量，再决定紧凑编码或有界分片。禁止静默截断。

新协议须区分已执行、部分可执行、缺少关联和能力不足，不能只确认收到消息。新旧语义使用独立版本和签名域，可以复用已有配对密钥；旧端不能被自动降级为整体音量执行器。

### iPad 的缺口

现有 iPad 产品实现不能履行新契约。公开 SDK 不提供 Mac Process Tap 的 iPad 支持；不能据此断言 iPad 运行时不存在同名实现，也不能把符号存在解释为功能可用。`AVAudioSession.duckOthers` 是本应用音频会话影响其他会话的机制，不能指定“保护另一个第三方应用、仅降低其余应用”。

2026-10-01 在已配对的 iPadOS 27.0 实机上运行独立开发签名探针，未激活音频会话、未创建录放音 I/O、未写入音量。通过运行时方法签名校验与已发现的属性键，取得以下证据：

| 探测对象 | 实测结果 | 能支持的判断 |
| --- | --- | --- |
| `AVSystemController` 的属性映射 | 存在 `RecordingClientPIDs`、`PlayingSessionsDescription`、`RecordingSessionsDescription` 等读取键。 | 来源观察不必局限于现有的全局录音 Bool。属性存在仍需实际活动验证。 |
| `PlayingSessionsDescription` | 返回一个第三方播放器的 `ClientPID`、`AudioSessionID`、`MXSessionIDs`，PID 与 Now Playing 应用对应。 | 普通开发签名在该条件下能读取第三方播放会话元数据；尚未验证多来源完整性与生命周期。 |
| 录音来源属性 | 当时 `IsSomeoneRecording=0`，录音 PID 和会话描述均返回 nil。 | 不能把 nil 当成稳定的“无录音”契约；实际录音期间的来源识别未验证。 |
| `AudioHardwareCreateProcessTap` | 动态符号存在，未调用创建。 | 不证明权限、捕获能力或选择性控制可用。 |
| HAL `dev#` / `prs#` | 设备列表成功返回空；进程列表大小为 0，零长度读取返回 `!siz`。 | 该探针条件下没有取得可用 HAL 对象，不能从该错误推断具体权限缺失或平台永久不支持。 |
| `AVSystemController` 写属性映射与方法元数据 | 能见到全局、分类、路由、打断相关接口；未取得可用的指定第三方会话增益入口。未调用任何写接口。 | 输出控制仍是独立缺口，不能从来源识别进展推出可选择性衰减。 |
| 使用真实会话 ID 查询对象 | `MXSessionManagerBase.copySessionWithAudioSessionID:` 与 `MXSession.copyMXSessionForID:` 均返回 nil。 | 拿到系统会话编号不等于探针进程持有可控制的会话对象；不能直接调用内部管理器假装已接入系统音频服务。 |

原始证据保存在本机忽略目录 `local/iPadAudioCapabilities/`，包括探针源码、构建及安装运行日志、`report-initial.json`、`report-query.json`、`report-sources.json`、`report-lookup.json`。已核对签名仅有 application identifier、team identifier 与调试 entitlement，没有额外的私有音频 entitlement。探针以 `--no-activate` 启动，采样时应用状态为 inactive；这不证明后台常驻或挂起状态下仍可查询。这些结果属于指定系统版本与签名条件下的实测，不是公开 API 的稳定保证。

继续推进后的受控实验发现客户端 `AVAudioSession.initProxySession:autoReconnect:` 可以为自产音源的自身会话建立代理，返回独立的 opaque session ID，source session ID 与音源会话相符，category 为 Playback。该次未启用自动重连、未激活代理、未写入任何代理音量或增益。此前 MXSession 的进程内查询返回 nil，不能被解释为所有客户端代理路径都不可用。

受控音源与原有播放器并行时，`PlayingSessionsDescription` 返回两个不同 PID/session 的记录；音源停止后仅剩原有播放器记录。前后集合断言通过，确认了这组来源的加入/移除行为。音源的渲染时钟在代理查询后仍递增；没有进行听感、实际输出增益或完整音频隔离测量。`getAllSessionInformation` 则全程返回空数组，不能取代已验证的 AVSystemController 会话描述。

首次同时安装被免费开发签名的三个安装名额限制。用户随后明确授权移除 Crafting Table，已移除并完成两个独立实验 App 的安装。修正后同版对照中，自产音源 PID 2846、session 463076 正在播放；音源自身代理成功，source session 相符，独立 opaque session 为 463078。另一个 App 的来源枚举同时匹配目标 PID/session，但 `initProxySession:autoReconnect:NO` 返回 nil，程序正常退出。音源渲染时钟持续增长，60 秒后正常停止。

第一轮跨应用探针曾在初始化后的 ARC 释放处崩溃；原因是将 init 方法当普通 `objc_msgSend` 函数调用，遗漏了初始化方法的所有权语义。改为已核对 ABI 的 Objective-C 方法声明后完成上述对照。该探针缺陷不是平台限制证据。

由此停止这一客户端代理候选的调查：本次 iPadOS 27.0、普通开发签名和调用条件下，没有取得第三方会话代理。不能进一步写成已经证明某项权限拒绝，也不能宣称所有 iPad 路径均不可能。没有写入任何代理增益或系统音量，录音来源识别和实际选择性输出仍未成立。

本轮不再进行无目标的私有符号搜索。推荐首阶段仅保留有证据支持的 iPad 能力；新协议明确报告未执行，不以整体媒体音量降级。可控网页或显式 App 集成作为后续候选，另行确定范围，不预建适配框架。由于这不能完整交付用户期望的 iPad 按应用协同，必须在计划复核时确认这个交付取舍。

源码和原始证据保存在忽略目录 `local/iPadAudioSource/` 与 `local/iPadAudioCapabilities/`，关键文件为各自的 `report-cross-app-fixed.json`、构建、安装与运行日志。两个临时 App 均已卸载，正式声邻未替换；Crafting Table 按用户授权移除，未重新安装。

## 实现计划草案（待用户复核，尚未开工）

### 统一行为契约

| 情形 | 安静需求 | 应保留的输出 | 解除条件 |
| --- | --- | --- | --- |
| 已确认的有效输入 | 请求降低允许控制的背景 | 同一逻辑应用实例及明确关联输出 | 输入结束或失去有效证据后按状态、租约处理 |
| 用户明确标记的通话，暂时静音或等待回答 | 不因保护标记单独新增安静需求 | 继续保留该通话输出 | 用户结束参与、关闭实例或有效应用结束信号 |
| 两个输入来源并发 | 合并请求，不叠乘增益 | 两者保护集合的并集 | 每个来源独立变化，不能只处理整体开始／结束 |
| 未观察到网页既有流，或状态未知 | 不能解释为已确认无输入；未知证据不续租旧请求 | 保留仍有效的用户保护 | 重新建立观察或明确结束参与 |
| 远程来源与本机输出没有明确关联 | 仅降低接收端明确允许的背景 | 本地有效输入和保护继续生效 | 不按应用名、域名或时间猜测关系 |
| 权限、设备或适配器故障 | 回报未执行／部分执行 | 撤销本产品增益，恢复原播放路径 | 能力恢复并重新核对实例后再执行 |

浏览器中的通话保护由用户显式参与标记维持，输入轨道观察仅提供输入证据。首版不从 ChatGPT DOM 猜测完整通话生命周期，也不把“已静音”解释为“可以压低对端声音”。后台网页调音和通话页输入观察分别授权；不需要降低的通话页不必为了保护输出而经过重放。背景页在用户调用时建立可控播放链，空闲时协调增益为 1；无法自动重建捕获授权时提示再次调用。

### 分步交付及完成条件

1. **共同状态模型与策略。** 在 `Shared` 中表达来源实例、输入证据、显式输出保护、关联和执行能力；`Mac/InputActivity.swift` 保留 PID 到逻辑应用的绑定。将 `MacGUI/AppModel.swift` 的布尔触发改为每次状态变化重算。输出为每个可控来源的目标协调增益与未执行原因，不直接写音量。用现有测试入口覆盖来源 A 换 B 但请求不归零、并发、静音、未知、关联及实例复用。
2. **Mac 原生执行器。** 以已验证的 Process Tap 加增益重放取代新模式下 `Mac/OutputVolume.swift` 的整机音量动作；只处理默认设备上可独立绑定的原生输出，排除声邻重放及由扩展管理的整个浏览器音频组。macOS 14.0–14.1 明确显示功能不可用，14.2 以上仍须检查实际授权和设备格式。受保护输出优先保持原路径；不能可靠归属的输出保持原状并报告能力不足。通过最终输出、异常恢复验收后才允许自动启用。
3. **浏览器本机适配器。** MV3 扩展通过 Native Messaging 向 Mac 提供绑定到浏览器连接、tab、document 的状态，并执行网页增益。Native Messaging host 只桥接本机消息，不承载音频，不创建新 peer；复用 App 的本机生命周期。首版只在用户调用的 ChatGPT 页面观察输入。输出捕获失败或播放链断开时释放该链并报告执行能力不足，同一文档仍有效的输入证据和用户保护继续保留；输入观察失效则标记未知，不续租缺少证据的请求，但保留有效用户保护。只有导航、刷新、关闭造成文档实例更换时，才撤销旧实例请求与保护，新实例重新建立状态。已在进行的 Voice 无法补观察时明确提示重启 Voice。本机控制采用一秒续租、五秒租约，避免 App 失联后背景网页长期保持衰减。扩展重载、连接丢失或本机控制租约到期必须释放捕获；Mac 同时撤销对应网页请求，仍把该浏览器混音整体排除原生衰减。
4. **多设备快照与回执。** 复用配对密钥、BLE/Wi-Fi、五秒续租和二十秒需求租约；新增独立消息版本及签名域，不发送旧 quiet 动作作为兼容降级。接收端每次收到有效更新均重算，回执区分已执行、部分执行、缺少关联、能力不足。旧端不参与新模式；iPad 缺少选择性执行能力时明确未执行。显式关联由用户在两端选择具体参与实例，自动模式仅影响被明确允许的背景输出。
5. **界面与现有文档。** 展示参与通话／背景、当前受保护对象、已调低对象、未接入网页和具体限制；设置中的“降低音量”改为相对协调增益，避免沿用整体系统音量阈值。更新 `docs/prd/index.md`、`docs/product-tdd/index.md`、`docs/index.md`、`docs/validation.md`，让旧整体音量说明与新语义一致。原有排除录音来源与麦克风静音功能须保留其独立含义。

每一步以可运行的最小纵向链路收尾，不先建设通用音频路由框架、浏览器分支或新的全局会话服务。Mac 与浏览器共同通过后再做完整远程联调；不以协议单测代替 iPad 功能验收。

### 有界快照

首版每设备最多发布四个参与来源；背景播放列表留在接收端，不占这个额度。静音或仅保留关联的参与来源仍计数，不能通过删除它们规避上限。来源 ID 与关联 ID 各为 128 位，不传 PID、网页句柄、标题或 URL。

候选编码使用 Codable JSON 短字段，固定版本、发起／响应角色、revision、有效期、快照状态、来源列表和 32 字节签名。编码使用 `withoutEscapingSlashes`，避免 base64 的斜线产生不必要膨胀；签名采用明确定义的规范字段序列，不能依赖 JSON 字典遍历顺序。`check-wire-budget.swift` 实际测量四项均带关联、最大整数和高斜线密度标识的长度为 BLE 415 字节、Wi-Fi 外层 442 字节；BLE 完整消息须不超过 512 字节，Wi-Fi 包含外层须不超过 1024 字节。

超过数量或实际编码上限时，不截断、不发布部分完整快照；发送紧凑的已签名容量不足状态，撤销该发送方的安静需求，保留接收端仍有效的本地保护及其他来源请求。首次实现不加入分片；真实需求超过四个并发参与来源，或必要字段超出预算时再评估有界分片。验收必须包含四项边界、第五项、最大字段、签名篡改、乱序、租约到期和旧版本。

### 实现验收与开工前决策

**开工前只剩浏览器输入注入时机的实际验证。** 用户已接受逐页调用和 ChatGPT Voice 基准；原生增益重放方向已有实验支持；iPad 当前候选的自身／跨进程对照已经完成。0.2.1 实验扩展增加只读输入观察，不启动麦克风、不读取 PCM，记录保存在文档隔离环境而非易休眠的后台全局变量：先在已加载页面调用，再开启 Voice，核对开启、静音、解除静音、结束；随后验证既有 Voice 和刷新不会被当作已完整观察。若页面缓存原始函数导致漏报，改为 ChatGPT 单站点权限加 document_start，再验证；不因此申请所有站点权限。

正式实现的验收包括：受保护路维持原音量、背景协调增益及解除恢复、最终输出没有重复原声；应用退出和强制终止、扩展失联／重载、权限拒绝、默认设备切换后不会持续静音；用户调整系统和应用音量后不被恢复成旧值。另须测量切换连续性、附加延迟和资源开销，覆盖 ChatGPT Voice 的实际输出、至少一组 WebRTC 合成对照、同站双页、导航、关闭重开及实例 ID 复用。iframe 输入在没有对应权限和证据时明确显示未知，不宣称任意网站全覆盖。

提交正式计划复核时，需用户确认两个实质边界：逐页授权下的 ChatGPT 首版范围（已接受），以及 iPad 首阶段能力不足时不执行第三方选择性调音的交付取舍（待复核）。用户已经明确要求先复核再开工，因此实验和文档完成不构成正式源码修改授权。
