后续在同一 Mac 上做了次缓冲对照：临时驱动把 `ProcessInput` 声明为非原地处理，并将结果写入 HAL 提供的次缓冲；签名安装后，两个 AUHAL 客户端仍在单独静音期间读到几乎相同的非零样本。因此仅改变该阶段的缓冲交付方式不能修复逐应用静音。实验驱动已卸载、源码已撤销，本地构建重新对应仓库源码；菜单栏 App 与默认 USB 输入均已恢复，自动协同保持关闭。

随后用单设备标记样本定位交付路径。临时驱动先在 `ReadInput` 和 `ProcessInput` 写入依赖客户端 PID 的不同常量：单个 AUHAL 进程读到自己的 `ProcessInput` 标记，两个并发进程却都读到两种标记之间的相同值。再让 `ProcessInput` 不修改样本，只在 `ReadInput` 为 PID 73120、73121 分别写入 0.220、0.221；两个进程每秒均读到约 0.2206，最小/最大千分值均为 220/221。这说明当前驱动的按客户端写入没有作为独立音频交付给两个应用，不能仅凭回调提供 PID 就认为逐应用静音成立。另试过启用 `ConvertInput` 并写入非原地次缓冲，但两个客户端都读到零，该变体没有正确供音，结果不能证明 `ConvertInput` 可行或不可行。上述实验版本均已卸载并撤销，正式源码和本地构建已恢复。

系统另有[进程输入静音](https://developer.apple.com/documentation/coreaudio/audiohardwaresystem/setisprocessinputmuted(_:))，但 macOS SDK 的 `kAudioHardwarePropertyProcessInputMute` 明确描述为“进入当前进程的所有设备数据静音”；[音频进程对象](https://developer.apple.com/documentation/coreaudio/audiohardwareprocess)提供 PID 与运行状态，却没有给其他进程设置输入静音的方法。不能把 Nearby 进程的这个开关当作任意应用的静音控制。单设备逐应用静音仍是未解决的能力问题，不能在菜单中呈现为已生效。

另一个临时原型在同一驱动中发布两个不同 UID 的虚拟输入设备，各有独立样本缓冲。两个 AUHAL 进程分别选择一台设备并同时取样；停止 A 的供源后，A 在第 9 秒的非零样本数为 0，B 同秒仍为 52,224；恢复 A 的供源后，A 第 10 秒恢复到 49,152，B 仍有 68,608。这仅是定位实验，不是产品方案；产品仍要求一个虚拟麦克风、在 Nearby 内按应用控制。原型驱动已卸载、源码已撤销，本地构建重新对应仓库源码；系统默认输入和 Mac 菜单栏 App 均已恢复。

继续开发时，在 macOS 15.4.1（24E263）上增加了带调用记录的单设备驱动原型。记录包括客户端 PID、bundle ID、输入时间戳、主/次缓冲地址及各阶段调用次数。HAL 只为首先启动的客户端查询一次 `WillDoIOOperation`，随后启动的客户端沿用这些处理步骤。分别尝试按客户端启用 `ProcessInput`、原地或次缓冲转换、在客户端 I/O 阶段返回错误，均未观察到目标客户端独立静音。输入流属性原型向两个客户端返回不同流的逻辑也未被使用：HAL 只以 PID 0 查询并缓存流列表，两个客户端均看到相同的两条流。驱动没有收到客户端对 `kAudioDevicePropertyProcessMute` 的查询；该属性由系统自身处理。以上观察将问题定位到 HAL 交付路径，不能仅靠在驱动输入回调里按 PID 改样本解决。

为了排除两个进程属于同一应用的影响，测试 App 分别使用 `local.nearbyaudio.probe.readerA`、`local.nearbyaudio.probe.readerB`，独立签名并在驱动记录中确认两个 bundle ID。`ReadInput` 标记和原地 `ConvertInput` 标记仍未独立交付。正向对照则成功：两个 App 使用同一个设备，A 调用系统的本进程输入静音后，第 2、3 秒各收到 96,256 个零样本；B 同时每秒收到 96,256 个非零样本。这个结果证明单设备上的进程隔离在系统中确实存在，当前缺少的是从 Nearby 或驱动控制其他未改造应用的可用入口，不能把本进程对照当作产品功能完成。

可重复的验收程序现位于 `experiments/VirtualMicrophoneProbe.cpp` 和 `scripts/test-driver-isolation.py`。脚本检查两个不同 bundle ID 的 App 是否选择同一设备，先确认合成供音和系统静音正向对照，再检查驱动对 A/B 分别静音、解除恢复和断源归零。所有阶段都要求收到足够数量的样本且没有渲染错误，避免把读取失败误判为静音。失败返回非零退出码，统计保存在本地忽略目录。调试原型及原始调用记录保留在本地 `local/SingleDeviceProbe/`，尚未提交版本控制。

这套验收先发现正式驱动的供音缺陷：每 20 ms 供给 960 帧、保持准确 48 kHz 时，基线半秒窗口中两端各有 48,128 个样本，却只有 19,456 个非零样本。驱动只留 512 帧余量，小于它接受的最大 2,048 帧供音包；此前每 20 ms 供给 1,024 帧的偏快测试会逐渐积累样本，掩盖供音间隔内的欠载。现将缓冲余量改为一个最大供音包，并向 HAL 报告这部分 2,048 帧（约 42.7 ms）延迟；断源恢复后只使用新供给的样本重新填充缓冲，避免回放上一次供音的旧数据。新增的最大包分批供音回归在旧代码上失败，修复后通过；另验证了恢复时不输出旧样本。这不代表长期时钟漂移已解决。

修复版签名安装后，完整双 App 验收得到：基线两端均为 48,128/48,128 个非零样本；系统静音 A 时 A 为 0/48,128、B 为 48,128/48,128；解除后都恢复。驱动静音 A 时，A 为 19,968/49,152、B 为 19,552/48,128；驱动静音 B 时，A 为 29,184/49,152、B 为 28,576/48,128。两次驱动静音均同时损伤两端音频，未实现隔离；解除后均恢复到全部非零。停止供源后两端均归零，所有阶段渲染错误数为 0。脚本正确以退出码 1 报告四项隔离断言失败，结果位于 `local/HALIsolationTests/results.json`。本轮测试驱动已卸载并重启音频服务，供音修复与验收代码保留在工作区，尚未提交。

进一步检查系统的跨进程入口时，在运行中的 AVFAudio 找到私有 `AVAudioApplication.initProxyForProcess:`。隔离探针能够取得自有目标进程的 audit token，但普通开发签名创建代理返回 nil，系统日志明确报告 `AVAudioApplication error - missing entitlement`。框架包含 `com.apple.private.coreaudio.borrowaudioapplication.allow` 权限名；仅给独立探针声明该权限并使用现有 Apple Development 身份签名后，静态签名校验通过，但系统在启动时终止探针。`taskgated-helper` 报告没有合格的 provisioning profile，AMFI 报告 restricted entitlements 校验失败。目标进程未被静音，产品 App 和驱动没有加入该私有权限，也未修改系统安全策略。探针位于本地 `local/SingleDeviceProbe/proxy-mute.mm`、`audio-app.mm` 和 `proxy.entitlements`。这证明当前签名无法使用该入口；尚未证明取得权限后它可以静音任意未改造的录音 App，不能把申请权限视为必然解决方案。

另核对了 [Apple 的 AudioDriverKit 示例](https://developer.apple.com/documentation/audiodriverkit/creating-an-audio-device-driver)及 Xcode 26.2 的 DriverKit 25.2 头文件。Apple 明确说明 AudioDriverKit 只支持物理音频设备，虚拟设备应使用 Audio Server Driver Plug-in。其输入流使用设备级环形缓冲，`IOOperationHandler` 接收设备、操作、帧数和时间戳，没有应用 PID 或客户端标识。现有证据不支持将当前虚拟驱动迁移到 DriverKit 就能获得逐应用输入控制，因此没有创建另一套驱动实现。

正式手动验收目前被单设备逐应用静音阻塞。进入验收前，`scripts/test-driver-isolation.py` 必须完整通过：同一个设备上的两个独立 App 持续收到有效样本，Nearby 分别静音任意一方时仅目标归零，解除后恢复，断源后两端归零且没有渲染错误；随后才进行真实 ChatGPT/Koe 与 iPad 联动验收。当前仍缺少可在产品签名下调用、可作用于未改造目标 App 的跨进程输入控制入口。下一项外部技术确认应向 Apple 核实此需求的受支持接口或可申请权限，并确认目标 App 是否需要配合；本轮没有向外发送报告。最终检查：系统 HAL 目录无 Nearby 驱动，Mac App 的自动协同关闭、输入进程数为 0、iPad 已连接且错误为空。

继续调查确认，Apple 的 macOS `AVAudioApplication` 文档及 WWDC23 示例要求目标应用自行处理输入静音回调；系统本进程静音属性可作为应用内部实现。因此即使私有代理权限获批，也尚不能保证未适配的任意第三方应用被静音。公开资料中未找到该私有权限的申请入口。已整理 [Apple 技术支持审核稿](apple-coreaudio-support.md)，集中询问单设备输入回调的隔离约定、受支持的跨进程入口和权限是否开放，不将实测失败预先定性为系统缺陷。
