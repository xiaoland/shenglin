# 多设备音量协同：跨端技术契约

本文件承接[产品要求](../prd/index.md)中已确认的多设备规则，记录各端互操作必须一致的职责边界。下文区分目标和当前实现；构建通过不等于真机互操作已验证。

少量已配对设备在逻辑上直接组成全连接：每端直接把**自己**的安静需求告知其他端，并在本机独立判断和执行收到的有效需求。不设置固定 Mac 中转、替别的设备转发需求、选主或共识。某个平台在蓝牙链路上担任 central 或 peripheral，只是传输角色，不改变产品中的对等地位。

需求来源是本机录音判断，音量执行是接收端的本机责任，按接收端持有的目标上限处理。接收端必须区分各来源的当前需求，让一个来源的结束不撤销其他来源，并保证重复状态不重复压低。请求在持续录音时续期；接收端短断连期间保留该来源，超过宽限且没有更新才释放。来源全部失效且本轮未被手动接管时，执行端平缓恢复。重连时双方对账当前状态，不重放旧指令，也不根据旧音量结果生成新需求。手动接管属于执行端的整轮状态，不能只在轮末根据当前数值猜测用户意图。身份、会话、版本、认证回执的具体协议和续期、宽限、渐变参数仍待复核，不在这里冒充已经选定的线上格式。

当前代码在既有 BLE 配对链路上增设了双向签名状态与签名回执，并增设一条经 Wi-Fi 的 Bonjour/TCP 双向传输。TCP 连接先用配对密钥完成带随机数的双向认证；Bonjour 发现本身不构成可信设备或空间证据。两条传输共用同一配对来源和递增版本，不能把重复状态算作两个请求。Mac 以 5 秒周期续期本机需求；接收端按来源和版本记录需求，接受的状态最多有效 20 秒。重发不重复调低，最后一项需求结束或过期后尝试渐变恢复。Mac 使用 Core Audio 控制默认输出设备；iPad 沿用媒体音量执行器，双方各自保存恢复快照和手动接管状态。旧 `ControlCommand.expiresAt` 仍只限制旧命令的接收时间，不代表新协议的租约。上述参数是待真机校准的当前实现值。

本轮代码仍沿用一对一配对；BLE 传输为 Mac central/iPad peripheral，Wi-Fi 传输为 Mac 监听/iPad 发起连接，网络角色不改变双方都能发起需求的产品语义。账本支持多个来源却没有三端连接实现。空间选择为 BLE 或 Wi-Fi、BLE 且 Wi-Fi 两种模式；Wi-Fi 证据仅指通过本地 Wi-Fi 路径完成配对密钥认证的局域网互通，不证明 SSID 或物理同室。短暂失去空间证据时保留上次已满足状态至多 20 秒，主动切换空间模式或暂停则立即重算。iPad 目前只发布 `quiet=false`：没有证据证明系统能可靠、持续地报告其他任意 App 的录音开始和结束，因此不能把 Mac 的反向接收代码计为已完成的 iPad→Mac 产品链路。iPad 暂停时撤销本机处理，Mac 暂停时停止发起及响应；后台回收时的租约计时和 Wi-Fi 连接仍需真机验证。详见[验证记录](../validation.md)。
