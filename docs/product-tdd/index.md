# 多设备音量协同：跨端技术契约

本文件承接[产品要求](../prd/index.md)中已确认的多设备规则，记录各端互操作必须一致的职责边界。下文区分目标和当前实现；构建通过不等于真机互操作已验证。

少量已配对设备在逻辑上直接组成全连接：每端直接把**自己**的安静需求告知其他端，并在本机独立判断和执行收到的有效需求。不设置固定 Mac 中转、替别的设备转发需求、选主或共识。某个平台在蓝牙链路上担任 central 或 peripheral，只是传输角色，不改变产品中的对等地位。

需求来源是本机录音判断，音量执行是接收端的本机责任，按接收端持有的目标上限处理。接收端必须区分各来源的当前需求，让一个来源的结束不撤销其他来源，并保证重复状态不重复压低。请求在持续录音时续期；接收端短断连期间保留该来源，超过宽限且没有更新才释放。来源全部失效且本轮未被手动接管时，执行端平缓恢复。重连时双方对账当前状态，不重放旧指令，也不根据旧音量结果生成新需求。手动接管属于执行端的整轮状态，不能只在轮末根据当前数值猜测用户意图。身份、会话、版本、认证回执的具体协议和续期、宽限、渐变参数仍待复核，不在这里冒充已经选定的线上格式。

当前配对信任记录统一为 `PairedPeer`：密钥标识一条已认证的配对关系，记录对端自报名称、平台和本端握手角色。平台决定目前可连接的传输组合，不决定对等音量协同的产品地位。Mac↔Mac 握手后先暂存密钥，实际 Wi-Fi 双向认证成功才正式保存；Mac↔iPad 也须通过新密钥的认证状态激活。协议采用 SPAKE2 版本 3，状态来源使用发起方/响应方角色；开发期不迁移旧配对，两端须一起更新并重新配对。设备改名在已认证 Wi-Fi 连接上以配对密钥签名同步。

当前代码在既有 BLE 配对链路上增设了双向签名状态与签名回执，并增设一条经 Wi-Fi 的 Bonjour/TCP 双向传输。TCP 连接先用配对密钥完成带随机数的双向认证；Bonjour 发现本身不构成可信设备或空间证据。两条传输共用同一配对来源和递增版本，不能把重复状态算作两个请求。Mac 以 5 秒周期续期本机需求；接收端按来源和版本记录需求，接受的状态最多有效 20 秒。重发不重复调低，最后一项需求结束或过期后尝试渐变恢复。Mac 使用 Core Audio 控制默认输出设备；iPad 沿用媒体音量执行器，双方各自保存恢复快照和手动接管状态。旧版 BLE 命令与回执回退已移除，BLE 只传递签名 peer 状态与回执。上述参数是待真机校准的当前实现值。

当前代码支持至少两台 Mac 与一台 iPad 的三条独立配对边：iPad 保存多台 Mac 的密钥，对已认证的 BLE central 分别返回状态和回执；Mac↔Mac 使用一次性码独立完成 SPAKE2 配对，随后直接通过按密钥发现的 Wi-Fi 链路传递状态，不借 iPad 转发。每条边分别判定空间条件并持有来源租约；一条边失效只撤销该来源。BLE 传输为 Mac central/iPad peripheral，Mac↔Mac 的 Wi-Fi 一端监听、一端连接，这些传输角色不改变产品语义。空间选择为 BLE 或 Wi-Fi、BLE 且 Wi-Fi 两种模式；Wi-Fi 证据仅指通过本地 Wi-Fi 路径完成配对密钥认证的局域网互通，不证明 SSID 或物理同室。Mac↔Mac 尚无 BLE 证据，因此严格 AND 模式对这条边保持关闭。短暂失去已满足的空间证据时保留上次状态至多 20 秒，主动切换空间模式或暂停则立即重算。iPad 通过只读的 `AVSystemController_IsSomeoneRecordingAttribute` 获取本机录音状态，不开启自己的麦克风；读数未知时不声明空闲，也不续期已有需求。语音备忘录录音和普通播放的区别已实测，iPad→Mac 音量协同已由用户真机验收；任意应用、锁屏和后台回收场景的可靠性仍不能据此推定。两端暂停时都撤销本机需求并停止响应；局域网实测和后台回收时的租约计时仍需真机验证。详见[验证记录](../validation.md)。
