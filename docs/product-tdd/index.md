# 多设备音量协同：跨端技术契约

本文件承接[产品要求](../prd/index.md)中已确认的多设备规则，记录各端互操作必须一致的职责边界。下文区分目标和当前实现；构建通过不等于真机互操作已验证。

少量已配对设备在逻辑上直接组成全连接：每端直接把**自己**的安静需求告知其他端，并在本机独立判断和执行收到的有效需求。不设置固定 Mac 中转、替别的设备转发需求、选主或共识。某个平台在蓝牙链路上担任 central 或 peripheral，只是传输角色，不改变产品中的对等地位。

需求来源是本机录音判断，音量执行是接收端的本机责任，Mac 按接收端的背景相对增益处理，iPad 按媒体音量上限处理。接收端必须区分各来源的当前需求，让一个来源的结束不撤销其他来源，并保证重复状态不重复压低。请求在持续录音时续期；接收端短断连期间保留该来源，超过宽限且没有更新才释放。来源全部失效时，Mac 解除本产品增益，iPad 在本轮未被手动接管时平缓恢复媒体音量。重连时双方对账当前状态，不重放旧指令，也不根据旧音量结果生成新需求。手动接管属于执行端的整轮状态，不能只在轮末根据当前数值猜测用户意图。当前协议保留设备级 `quiet/known/revision` 与租约，不传递应用身份或跨端关联；`targetMilli` 仅表示 iPad 媒体音量上限。

当前配对信任记录统一为 `PairedPeer`：密钥标识一条已认证的配对关系，记录对端自报名称、平台和本端握手角色。平台决定目前可连接的传输组合，不决定对等音量协同的产品地位。Mac↔Mac 握手后先暂存密钥，实际 Wi-Fi 双向认证成功才正式保存；Mac↔iPad 也须通过新密钥的认证状态激活。协议采用 SPAKE2 版本 3，状态来源使用发起方/响应方角色；开发期不迁移旧配对，两端须一起更新并重新配对。设备改名在已认证 Wi-Fi 连接上以配对密钥签名同步。

当前代码在既有 BLE 配对链路上增设了双向签名状态与签名回执，并增设一条经 Wi-Fi 的 Bonjour/TCP 双向传输。TCP 连接先用配对密钥完成带随机数的双向认证；Bonjour 发现本身不构成可信设备或空间证据。两条传输共用同一配对来源和递增版本，不能把重复状态算作两个请求。Mac 以 5 秒周期续期本机需求；接收端按来源和版本记录需求，接受的状态最多有效 20 秒。重发不重复调低，最后一项需求结束或过期后尝试渐变恢复。Mac 用 Process Tap 处理默认输出设备上可归属、未受保护的播放进程，加增益后原设备重放，不修改系统音量；旧整机快照只用于一次迁移恢复。iPad 沿用媒体音量执行器，保存恢复快照及整轮手动接管状态。旧版 BLE 命令与回执回退已移除，BLE 只传递签名 peer 状态与回执。上述参数是待真机校准的当前实现值。

当前代码支持至少两台 Mac 与一台 iPad 的三条独立配对边：iPad 保存多台 Mac 的密钥，对已认证的 BLE central 分别返回状态和回执；Mac↔Mac 使用一次性码独立完成 SPAKE2 配对，随后直接通过按密钥发现的 Wi-Fi 链路传递状态，不借 iPad 转发。每条边分别判定空间条件并持有来源租约；一条边失效只撤销该来源。BLE 传输为 Mac central/iPad peripheral，Mac↔Mac 的 Wi-Fi 一端监听、一端连接，这些传输角色不改变产品语义。空间选择为 BLE 或 Wi-Fi、BLE 且 Wi-Fi 两种模式；Wi-Fi 证据仅指通过本地 Wi-Fi 路径完成配对密钥认证的局域网互通，不证明 SSID 或物理同室。Mac↔Mac 尚无 BLE 证据，因此严格 AND 模式对这条边保持关闭。短暂失去已满足的空间证据时保留上次状态至多 20 秒，主动切换空间模式或暂停则立即重算。iPad 通过只读的 `AVSystemController_IsSomeoneRecordingAttribute` 获取本机录音状态，不开启自己的麦克风；读数未知时不声明空闲，也不续期已有需求。语音备忘录录音和普通播放的区别已实测，iPad→Mac 音量协同已由用户真机验收；任意应用、锁屏和后台回收场景的可靠性仍不能据此推定。两端暂停时都撤销本机需求并停止响应；局域网实测和后台回收时的租约计时仍需真机验证。详见[验证记录](../validation.md)。

Mac 每 250 毫秒更新输入身份、输出集合及保护，不只响应请求整体开始或结束。原生输出绑定同时核对 AudioObjectID、PID、进程启动时间和应用身份，排除自身重放、浏览器家族及无法归属的输出。首版仅支持 macOS 14.2 以上默认输出的单流、无物理输入流、双声道交错 Float32 路径；权限、格式及运行失败均撤销 Tap，不回退整机降音量。强制退出后的原声恢复属于必须实测的发布门槛。

MV3 扩展以 activeTab 授权，Native Messaging host 使用固定扩展 ID，只将本机网页快照与增益命令桥接至现有用户私有 Unix socket。每连接最多 64 个文档、总共最多 16 个连接，消息上限 32 KiB，超限拒绝。tabId 用于执行，documentId 用于参与实例；同文档 SPA 导航保留保护，刷新或文档替换撤销旧参与。每秒续期、五秒本机租约，断线或过期释放背景捕获。只有显式背景页经过 AudioContext 重放，通话页保留原输出。轨道观察只适用于授权页，不读取或传送音频；页面报告可能伪造，不能作为系统身份或其他网页的可信证据。

浏览器的网页需求由扩展判断，HAL 浏览器输入只作诊断。`known` 描述已纳入来源的聚合需求：有确认需求时为已知安静；没有确认需求且参与来源观察失效时为未知；全部参与来源明确静音或结束时为已知结束。未接入网页不参加这个聚合，不能让明确静音继续续租。未知状态保留旧远端请求至原租约到期而不续期。

iPad 每秒及每次有效远端更新都重算执行条件。本机录音或未知时立即恢复仍属于声邻的改动，并监测暂停基线；用户修改或路由变化使该轮交给用户。暂停不撤销远端需求，不清除手动接管；本机确认空闲后，仅未接管的一轮允许继续。音量读取或恢复失败须报告，不能以系统 ducking 为由宣称恢复成功。

浏览器 API 边界以 [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) 和 [runtime 消息接口](https://developer.chrome.com/docs/extensions/reference/api/runtime) 为依据；离屏文档只接受本扩展非标签页来源的播放命令。主动 disconnect 不会对本端派发 onDisconnect，因此执行端须同步清理自己的连接状态；不能只等待回调。
