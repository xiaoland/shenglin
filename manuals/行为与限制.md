# 行为与限制

Android 使用 `AudioManager` 的公开匿名录音配置和回调，报告系统是否存在活动录音，不识别具体应用、不占用麦克风。用户开启协同时运行带常驻通知的 `connectedDevice` 前台服务；厂商后台策略、用户强制停止和系统回收仍可能中断协同。Android 调整的是系统媒体音量档位，不改变通话或铃声音量。本机录音或观察未知时撤销仍由声邻持有的调整，并保留远端请求至原租约结束。

Android 按周期和每次请求前的实际音量读数判断外部修改；检测到外部修改或输出路由变化后，整轮让权。公开接口不能区分实体音量键、系统与其他应用写入，也无法发现两次检查之间调走又调回完全相同值的操作。Android 13 起按媒体属性查询输出路由；旧系统只在可明确判断的单输出路径上执行，固定音量或不明确路径保持原状并报告不可用。恢复快照只适用于仍匹配的输出和音量，读写失败不报告成功。

新通用局域网配对认证双方平台和名称，配对码本身不发送。每条 Android、Mac、iPad 关系直接通信，收到远端请求不会再转发成自己的录音需求。Android 与 Mac、iPad、Android 的配对关系可通过蓝牙和局域网独立传递签名状态，网络范围可选 Wi-Fi 或局域网，再与蓝牙按“或”或“且”组合。Wi-Fi 条件要求本地实际连接和对端签名声明的连接介质均为 Wi-Fi；Wi-Fi 与网线混用仅满足局域网，不保证相同 SSID 或同室。旧版本若不提供介质证明，仍能完成局域网身份认证，但需更新才能提供 Wi-Fi 条件证据。只有实际完成认证的链路才提供证据；权限未授予、硬件不支持或蓝牙关闭时，不以局域网代替蓝牙满足“且”条件。旧 Apple 配对关系继续保留。Android 密钥经 Android Keystore 保护后保存在应用私有存储，禁止云备份；Apple 端仍使用 Keychain。

Mac 原生输入用公开 Core Audio 接口每 250 毫秒观察各进程是否有活动输入流，不根据原生应用内“静音”状态或是否有人说话作判断。浏览器输入由用户授权的扩展观察网页轨道；HAL 浏览器活动只作诊断。同一 `.app` 内的辅助进程可匹配外层应用。排除应用只阻止向其他设备发出安静请求；它在 Mac 本机录音时仍会触发本机协同，自己的输出始终受保护；只使用已静音专用麦克风时停止安静需求，但保留输入应用的输出保护。用户手动改动 iPad 音量或切换输出设备后，恢复步骤会保留新状态；如果调走后又调回程序设置的完全相同数值，现有检查无法辨别。

成功返回空输入设备列表的系统或 tap 进程不算作麦克风客户端，也不会阻断其它输入。若 Core Audio 属性或排除配置暂时无法读取，Mac 会显示输入状态不可用并停止降音量请求；恢复读取后自动按实际输入状态继续。故障期间正在录音的应用可能使远端恢复正常音量。菜单栏的绿色连接状态表示已收到 iPad 认证回执或已有完成双向认证的 Mac 直连；蓝牙订阅成功但尚未得到回执时显示为等待确认。

当前触发条件是“未排除的应用有活动输入流”；通过本产品静音的虚拟麦克风客户端不触发降音量。直接使用其他输入设备的应用不受本产品静音开关影响，但仍可参与 iPad 音量协同。原生应用内部的静音状态不会由本产品推断或控制；已接入 ChatGPT 的同一音轨需同时 live、enabled、未 muted 才形成有效输入，软件静音不撤销显式输出保护。

蓝牙与 Wi-Fi 的 peer 状态带有效期、递增版本和 HMAC。有效期校验允许发送方时钟最多领先接收方 5 秒，避免微小时差在整数秒边界触发误拒绝；已经过期的消息仍被拒绝，接收方记录的安静请求最多持续本机时间 20 秒。超过容差的时差需要校准设备时间。蓝牙传输中，Mac 等待 iPad 签名的应用执行回执，而不把蓝牙写入确认当作音量已改变。配对使用固定版本的 [BoringSSL SPAKE2](https://github.com/google/boringssl/blob/main/include/openssl/curve25519.h)：六位码参与密码认证密钥交换，双方再以独立方向的证明确认同一密钥。验证码不存为长期控制密钥。它是 App 自身的配对流程，并非系统蓝牙配对认证。控制密钥留在各端 Keychain；iPad 仅在收到新密钥认证的控制状态时添加该 Mac，Mac 验证该状态的 iPad 回执后才将其加入设备列表。Mac↔Mac 双方在新的 Wi-Fi 认证链路建立后才正式保存配对。Mac↔Mac 配对在局域网传输握手消息，验证码本身不发送。非秘密的序号存本机偏好。iPad 音量控制使用在目标设备上实测的私有 `AVSystemController` 媒体接口，系统更新后可能需要重新验证。

iPad 不用静音播放保活、不打开麦克风，也不伪造通话。录音检测依赖 iPadOS 私有属性，在目标设备上已完成前台只读对照，但后台、锁屏和系统更新后的行为仍需真机复验。读数不可用时发送“未知”状态，既不立即撤销安静请求，也不续期；既有请求最迟按 20 秒租约到期。蓝牙断线时尝试恢复并自动重连，但系统回收 App、用户强制退出、设备重启后第一次解锁和长时间断线不能保证无条件自动恢复。蓝牙可达也不等于同房间。Mac↔Mac 当前只有局域网认证证据，因此空间条件选“蓝牙且局域网”时两台 Mac 不互相降音量。只验证了媒体音量，没有验证铃声、通知或通话音量。真机证据和待验边界见 `docs/validation.md`，此前可行性实验见 `docs/feasibility.md`。多端剩余验收见[任务包](../tasks/multi-device-volume/packet.md)。

Mac 新输出链不写系统音量。应用归属来自外层 `.app`、bundle 和可执行文件身份；同一应用辅助进程可共同受保护，不能可靠归属的输出保持原状。进程接管同时核对启动时间，避免 PID 复用。首版只处理默认设备上的无输入流、单输出流、双声道交错 Float32 路径，多设备或不支持的设备保持原状；macOS 14.0–14.1 不支持此原生执行器，不用整机音量降级。

浏览器首版按用户调用后的文档实例参与，不申请全站长期权限。页面可以伪造自己提供的轨道元数据；声邻只把它用于用户授权页的参与判断，不当作系统身份或其他网页的证据。首次基准是 ChatGPT Voice，不保证任意网页、iframe、浏览器版本或未来实现。未接入的网页不会被粗略的浏览器混音一并降低。Native Messaging 只传本机元数据与增益，音频不离开浏览器；原生 Tap 音频只在内存中处理，不加入专用麦克风诊断录音。

iPad 本机录音或未知时让出媒体音量控制，不替第三方应用设置音频会话。系统 ducking 取决于对应应用选择的会话选项。暂停期间继续观察手动音量与路由变化；已低于目标时也记录观察基线，避免之后覆盖手动提高音量。恢复写入或读取失败保留原快照并重试，不等同用户接管。iPad 仍受后台计时及私有接口限制，不能承诺系统挂起后即时恢复。

Windows 版目前为 x64 命令行服务，使用 WASAPI 共享模式采集与会话音量，不修改系统总音量。配对与共享操作需要管理员终端；Windows 隐私设置和驱动能力仍约束实际输入。已配对不等于共享麦克风，须逐 peer、逐输入授权。Windows 服务自身的供源采集不作为本机录音需求，避免远端录音被重复反馈成新的本机来源。

远端麦克风首个可用方向为 Windows→Mac。音频使用已配对关系派生的双向会话密钥加密，限局域网物理接口；发现记录不构成授权，录音时重新认证并持续检查授权。断线输入静音、在线后按需重连；不会自动改用本地物理麦克风。当前固定48kHz单声道、20ms包，不承诺互联网、专业低延迟或多小时连续录音。Mac HAL 的现有本机诊断会记录客户端读到的音频，Windows 服务不保存PCM；声音不会由本功能自动上传到外部服务。
