# 开发与诊断

共同协议与协同规则位于 `Core/` Rust crate，通过 UniFFI 生成 Swift/Kotlin 绑定。先运行 `scripts/build-rust-core.sh test` 执行兼容回归，`macos`、`ios`、`android` 或 `all` 构建各平台库。Rust 工具链、目标标准库、JDK 17、Android SDK 36/NDK 以及 Xcode 需预先安装；Cargo 依赖由锁文件固定，缓存、生成绑定和产物保存在仓库 `local/`。当前 `ios` 只构建 arm64 真机。PAKE 仍使用固定版本 BoringSSL，由 Rust 统一调用 `NativePAKE` C 实现，应用不再单独维护 Swift/JNI 配对桥。

Android 工程位于 `Android/`，生产代码使用 Kotlin，界面采用 Jetpack Compose 与 Material 3。设置 `ANDROID_HOME` 指向 SDK 后运行 `scripts/build-android.sh`，执行单元测试并生成调试 APK。Android Studio 不是构建依赖。Android 不请求录音权限，`RecordingObserver` 只观察系统配置；`PeerService` 持有前台服务与本机音量执行，`transport/PeerTransport` 和 `ble/` 管理平台连接与发现，`core/` 是 Rust 绑定的薄适配。

在 macOS 上运行 `python3 scripts/test-android-interop.py`，会编译实际 Swift/Kotlin 接入，检查 Android↔Mac、Android↔iPad 双向握手、Android↔Android 和旧 v3 配对的密钥确认、平台身份与状态签名。`--legacy-dir` 可使用迁移前留存的 interop 目录检查混合版本。该测试不模拟无线发现，也不能代替设备后台和音量验收；真机还须确认覆盖安装无需重新配对、真实录音触发与恢复、手动接管和断连超时。


互操作脚本还生成 `local/AndroidInterop/wifi-peer`。在 Mac 可互通的局域网上运行 `local/AndroidInterop/wifi-peer mac`（或 `ipad`），它广播“声邻互操作探针”并输出测试验证码；Android 可从发现列表配对。反向验收可运行 `local/AndroidInterop/wifi-peer mac --client`，等待设备列表后输入 `choose 设备名`，连接就绪后输入 `code 六位码`。标准输入 `quiet`、`idle`、`quit` 分别模拟需求开始、结束、退出，标准输出记录实际认证与回执。探针复用 Swift 真实传输代码，但不读取 Mac 音频、不修改正式 Keychain；它模拟的平台标签不是完整 Mac/iPad App 的验收结果。加 `--ble` 可在 Mac 探针通过局域网认证后启动真实蓝牙 central；`lanoff` 停止局域网但保留蓝牙，`bleoff` 停止蓝牙，便于验证两种配置及宽限。该模式只用于 Mac 标签，不能用它证明 iPad 的 peripheral 行为。测试结束后从 Android 移除探针配对，避免留下只在本次进程存续的临时关系。

验证 Android 作为蓝牙 central 的路径，可运行 `scripts/build-android-ble-peripheral-probe.sh`，再按构建输出启动隔离命令行测试端。它在 Mac 上模拟 iPad 标签的已配对 GATT peripheral，支持 `quiet`、`idle`、`lanoff`、`quit`，并记录状态、回执与协商 MTU。此探针不访问正式配对存储或音频，也不代表真实 iPad 的后台与蓝牙行为。

Mac 图标使用传统 `.icns`：`Design/AppIcon.svg` 在 1024 像素画布上保留 100 像素外围透明留白，主体宽 824 像素，与 macOS 15 系统图标的绘制范围一致。调整此矢量稿后运行 `scripts/build-macos-icon.sh`，重新生成 `MacGUI/AppIcon.png` 和含全部十档分辨率的 `AppIcon.icns`；重生成工具需要 librsvg，正常构建使用已提交资源。16/32 像素版本减小留白以保持可辨认性。不要把铺满画布的 iPad 图标直接装入 Mac 的 `.icns`。若改用新版 Icon Composer，应按 Apple 的[使用说明](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer)将 `.icon` 加入工程，让 Xcode 处理平台样式；导出的 PNG 不能替代这一步。

在 Apple Silicon Mac 上用 Xcode、命令行工具和 CMake 开发；缺少 CMake 时，`build-pake.sh` 会在忽略版本控制的 `local/` 中通过 Python/pip 安装。脚本从固定的 BoringSSL revision 下载源码，版本变更时重建 Mac 与 iPad 静态库；源码、产物及本机签名信息不提交，许可证见 `third_party/BoringSSL-LICENSE.txt`。项目面向 arm64 Mac 与 iPad 真机；未验证 Intel Mac 或模拟器。当前构建验证使用 Xcode 26.2。

```sh
scripts/build-rust-core.sh both
swift test
python3 scripts/test-mac-presentation.py
python3 scripts/test-ipad-installation.py  # 隔离验证 iPad 安装流程，不操作设备
swift build -c release  # 仅构建调试用 CLI，不生成菜单栏 .app
xcodebuild -project MacGUI/ShenglinMac.xcodeproj -scheme ShenglinMac -configuration Release -sdk macosx -destination 'generic/platform=macOS' -derivedDataPath local/MacDerived CODE_SIGNING_ALLOWED=NO build
xcodebuild -project iPad/ShenglinPad.xcodeproj -scheme ShenglinPad -configuration Debug -sdk iphoneos -destination 'generic/platform=iOS' -derivedDataPath local/iPadDerived CODE_SIGNING_ALLOWED=NO build
scripts/build-driver.sh  # 构建并离线测试虚拟麦克风驱动，默认不签名、不安装
```

需要可运行的 Mac 应用时，确保本机已有 Apple Development 证书，再从主仓库运行 `scripts/build-mac-app.sh`；脚本默认使用该签名身份，也可设置 `SHENGLIN_SIGN_IDENTITY` 指定证书。脚本先签名并验证暂存 App，确认 GUI 已退出后停止旧后台服务，再替换 `dist/` 中的旧构建；重新打开 GUI 会注册新版服务。制作测试版 DMG 时运行 `scripts/package-macos-dmg.sh`；它会验证 App 签名并生成 `dist/Shenglin-macOS-arm64.dmg`，但不会把开发签名变成公开分发签名，详见[安装与分发](安装与分发.md)。开发时运行 `scripts/run-mac-app.sh` 会在后台打开主仓库的签名包，不抢占正在使用的窗口，并检查是否已有其他路径的 声邻GUI。不要从工作树的 Xcode 构建目录启动第二份 App。iPad 工程只有 Debug 配置：可从 Mac 声邻“设置…”→“iPad 安装”构建、签名并覆盖安装，操作见[安装与分发](安装与分发.md)。命令行开发仍可先运行 `scripts/build-rust-core.sh ios`，然后在 Xcode 中选择自己的开发团队与 iPad 真机，签名并安装。`scripts/package-ipad-ipa.sh` 从无签名构建生成供安装者自行签名的 IPA，不会安装或替换设备上的应用。安装新构建后需另外验证蓝牙连接、配对状态及音量回执。

浏览器扩展在 `BrowserExtension/` 中使用 [WXT](https://wxt.dev/guide/essentials/entrypoints) 和 [Vue 官方模块](https://wxt.dev/guide/essentials/frontend-frameworks)。开发需要 Node.js 22.12 或更新版本及 pnpm 11.20.0；首次拉取或锁文件变化后运行 `pnpm --dir BrowserExtension install --frozen-lockfile`。`pnpm --dir BrowserExtension run dev` 启动开发构建与热更新，然后在现有 Helium 中加载 `BrowserExtension/.output/chrome-mv3-dev`；默认不另起浏览器配置，以便沿用本机 Native Messaging 设置。`pnpm --dir BrowserExtension run build` 生成可手动加载的生产扩展 `BrowserExtension/.output/chrome-mv3`；源码目录不能直接加载为扩展。开发输出含调试服务配置，不能用于 App 分发。Xcode 的 “Build Browser Extension” 阶段调用 `scripts/build-browser-extension.sh`，只将成功构建的生产目录复制到 App 资源的 `BrowserExtension`，构建失败会阻止打包；构建阶段不自动安装 pnpm 依赖。终端已配置的 Node 路径需对 Xcode 可用，脚本支持本机 mise shims 与常见 Homebrew 安装路径。

`entrypoints/popup/App.vue` 持有弹窗显示与操作状态，`entrypoints/background.js` 持有逐页授权、Native Messaging 连接和租约，`entrypoints/offscreen/` 负责浏览器内音频重放；`input-bridge.js` 和 `input-main.js` 是用户选择通话后才注入的独立入口，不在 manifest 中自动注册。图标位于 `public/icons/`，固定扩展 key、权限和其他全局声明由 `wxt.config.ts` 维护，版本由 `package.json` 维护。不要更换 key，否则 Mac Native host 的扩展身份校验会失效。运行 `pnpm --dir BrowserExtension test` 会先构建生产产物，再执行 Vue 实际挂载测试、生产脚本的输入/捕获/重连回归和 manifest 约束检查；协调回归通过 Node 的实验性 VM Modules 执行打包后的模块，因此会有实验性 API 提示。`python3 scripts/test-browser-native-host.py` 在已有生产构建及正式安装的 App 上验证本机协议。

虚拟麦克风驱动位于 `Driver/`，基于固定版本的 [libASPL](https://github.com/gavv/libASPL/tree/v3.1.2)；`scripts/build-driver.sh` 将依赖放在忽略版本控制的 `local/`，生成 `local/DriverBuild/ShenglinDriver.driver`，许可证见 `third_party/libASPL-LICENSE.txt` 及相邻的 Apple 示例许可证。设置 `SHENGLIN_SIGN_IDENTITY` 可在构建后用指定身份签名并验证驱动；安装仍需管理员把驱动放入 `/Library/Audio/Plug-Ins/HAL`，随后重启音频服务或 Mac。构建脚本不执行安装。专用设备列表由 HAL 存储，应用选择按 bundle ID 存在 `microphones.json`；旧版 `muted.json` 不会自动批量创建设备。两次 120 秒真实 USB 输入到虚拟设备的双客户端闭环已通过，长时通话、拔插和睡眠唤醒仍待验证，详见[验收记录](../docs/validation.md)。

先退出 声邻GUI，再用 `python3 scripts/test-driver-isolation.py` 检验已安装驱动。它临时添加两台专用设备和两个不同 bundle ID 的测试 App，验证各设备独立静音、恢复和断源归零，再恢复原设备列表。脚本只供给合成音频，不安装驱动或改变默认输入；不要与运行中的 声邻同时修改设备列表。签名身份读取 `SHENGLIN_SIGN_IDENTITY`，未设置时使用临时签名，统计在 `local/HALIsolationTests/results.json`。旧单设备隔离失败的复现快照保留在本地 Apple 支持附件中，不是当前产品路线。


SwiftPM 的 `.build/release/shenglin` 支持 `control status|pair start|pair choose <UUID>|pair code|pair cancel` 等本机诊断命令；运行中的 GUI 通过同一用户的 Unix socket 执行它们。`pair code` 从标准输入读取验证码，不从命令参数读取。CLI 还保留 `sources`、`exclude list|add|remove`、`mute list|add|remove`。CLI 与 GUI 共用排除及静音配置；蓝牙控制由 GUI 统一持有。`control microphone add|remove <bundle ID>` 可添加或移除专用设备，`control mute add|remove <bundle ID>` 控制已分配设备。`control status` 按已配对设备返回各自链路、空间条件及目标音量，并返回应用设置、活动进程数、最后一次认证回执及错误；`control target <设备 ID> <0...0.5>` 只更改指定 iPad 的目标音量；超时或连接失败先检查菜单栏 App 是否运行。分享诊断输出前应删去设备名、UUID 和应用列表。仓库不包含配对密钥、设备标识、开发证书或本机日志；不要用会输出 Keychain 密钥内容的命令排障。

Mac 主窗口和设置使用系统分组表单，配对使用独立弹窗。`python3 scripts/test-mac-presentation.py` 编译实际展示与关闭会话代码，检查状态汇总、验证码输入和关闭弹窗保留已验证配对的边界；外部会话由隔离对象代替，不访问音频、网络或 Keychain。这项检查不替代真实设备配对与音量验收。

代码入口：`MacGUI/AppModel.swift` 持有菜单栏状态、各 peer 会话和本机控制命令；`Mac/MicrophoneAgent.swift` 在独立的 launchd 进程中持有专用设备的采集与驱动写入；`Mac/MacPairing.swift` 管理 Mac 直连配对；`Mac/InputActivity.swift` 报告未排除、未由虚拟麦克风静音的活动输入，`Mac/VirtualMicrophone.swift` 按需采集物理输入并供给 `Driver/Driver.cpp`，`Mac/BLEClient.swift` 负责 BLE 双向状态及回执，`Mac/OutputVolume.swift` 控制本机默认输出音量。`iPad/RecordingActivity.swift` 只读系统录音状态，`iPad/BLEServer.swift` 校验状态、管理配对激活，`iPad/Volume.swift` 保存及恢复媒体音量。各端共用 `Shared/Protocol.swift` 的 BLE 标识与认证工具、`Shared/PeerState.swift` 的来源租约和空间规则、`Shared/WiFiPeer.swift` 的 Bonjour/TCP 认证通信，以及 `Shared/PairingProtocol.swift` 的 SPAKE2 握手。iPad 录音探针已在目标真机观察到空闲为 0、语音备忘录录音时为非零、结束后回到 0，普通播放保持 0；正式 iPad→Mac 降音量已由用户真机验收；锁屏和多设备场景仍待验证。Wi-Fi 及三端全连接也未完成真机验证，详见[多设备任务包](../tasks/multi-device-volume/packet.md)。修改 BLE 标识或签名字段会改变设备间协议，需同时验证两个 App 工程。

音频占用的排查方法、本轮实机采样及隔离对照见 [Mac 音频性能分析](../docs/mac-audio-performance.md)。输入查询与取证状态的回归检查分别运行 `sh scripts/test-input-activity.sh` 和 `sh scripts/test-forensics-retention.sh`；两者在隔离边界验证行为，不访问真实录音或修改已安装驱动。
